# 0042. Автотесты UI на стенде ГУ — свои, через OCR Windows и эталоны, без LLM

- Статус: принято
- Дата: 2026-11-16
- Источники: PR #239, `pc-headunit/autotest/`, README там же

## Контекст

Перед релизом нужно пройти все экраны рабочего стола на всех языках и с переключением настроек. Вручную на машине
это долго. Смотрели google/artemis и аналоги, но они рассчитаны на Android-экран, а ГУ видит только видеопоток
CarLife.

## Решение

Свой фреймворк на Python поверх эмулятора ГУ `carlife_hu.py` (Егор 16.11: «делаем своё»). Тест тапает в пиксели
видео, текст находит через OCR Windows (`Windows.Media.Ocr`), кадр сравнивает с эталоном PNG по маскам. Без LLM.
Тексты в сценариях записаны ключами строк приложения, поэтому один сценарий проходит на всех пяти языках.

- OCR Windows, а не rapidocr: модели rapidocr читают кириллицу как латиницу («Настройки» → «HacTpoMK»).
  Для каждого языка нужен свой пакет OCR Windows (`Add-WindowsCapability`). Кадр увеличивается в 1,5 раза, иначе ar
  и zh теряют короткие слова.
- Смена языка = перезапуск и повторная активация smoke (~20 с). От языка зависят навигаторы и раскладка, а их
  `LauncherModel` считает один раз.
- На время прогона autoplay лаунчера выключен, а медиа стоит на паузе. Иначе подключение запускает последний плеер, и
  главный экран и порядок плееров меняются от прогона к прогону.

## Альтернативы

- google/artemis и похожие (UI Automator, Espresso): не видят экран ГУ, это виртуальный дисплей в видео.
- Скриншот-тесты Compose на JVM (Roborazzi): быстрее и без телефона, но не проверяют путь тап → мост → видео.
  Возможное дополнение для полной матрицы настроек, не замена.

## Последствия

Эталоны зависят от профиля ГУ, размера, языка, темы и цветов: `refs/<hu>-<W>x<H>/<язык>/`. Плавающие области (часы,
статус, живые плитки) закрываются масками. Маски закрашиваются в сохранённом эталоне, потому что репо публичный.
