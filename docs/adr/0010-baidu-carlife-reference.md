# 0010. Эталон поведения — Baidu CarLife 8.6.7; отличие от него считается ошибкой

- Статус: принято
- Дата: 2026-10-26
- Источники: PR #5, #18, #68, #83, #119, реверс `libencryption.so` и `com.baidu.carlife.*`, `CarLifeSession.kt:392`, `:603`, `:628`, `Handshake.kt:128`

## Контекст

ГУ тестировались производителями только против настоящего Baidu CarLife. Любое отличие нашего поведения (порядок
сообщений, размер write, пауза) ГУ может истолковать как сбой и оборвать сессию. Спецификации протокола недостаточно.

## Решение

Если ГУ ведёт себя странно, сначала смотрим, что делает Baidu 8.6.7 (реверс), и повторяем это. Так сделано:

- авторизация 2.0: `md5hex("CARLIFE" + brand + model + sdk + дата)` (PR #5); Mobis CCNC шлёт «1» без «2.0;», Baidu
  на это молчит — молчим и мы (`CarLifeSession.kt:392`);
- heartbeat на PAUSE (0007);
- rejoin Wi-Fi Direct при распаде группы по образцу `WifiDirectDiscoverManager` (PR #68, 0014);
- запись AOA одним write и MIC/WAKEUP как `VrManager` (Mobis, PR #119, 0009);
- `CAR_DATA_START` только в ответ на RSP и только для объявленных модулей. Слепой START (даже один OIL) вешает видео
  Vezel; подтверждено в двух ветках 25–26.10, топливо с приборки закрыто. В `main` сообщение не отправляется
  (есть только `CAR_DATA_SUBSCRIBE`, `Handshake.kt:128`).

## Альтернативы

- Слепые `CAR_DATA_START` — вешают видео, отвергнуто.
- Собственное толкование протокола там, где Baidu ведёт себя иначе — отвергнуто как правило работы.

## Последствия

- Перед новым обходом искать аналог в декомпиляции Baidu; без него правка рискованна.
- Реверс не содержит всего: где Baidu молчит, догадки нужно проверять на машине.
- Версия 8.6.7 совпадает с `versionName` legacy-APK (0013).
