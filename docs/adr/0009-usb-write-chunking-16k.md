# 0009. Запись в USB: заголовок отдельно, тело кусками до 16 КиБ, с исключениями

- Статус: принято
- Дата: 2026-10-20 (PR #89), 2026-10-30 (PR #119)
- Источники: PR #89, #119, кейсы h238, h242, h359, `Protocol.kt:249`, `:300-321`, `link/StreamTransport.kt:25`, `:150`, `CarLifeSession.kt:746-752`, `:1150`

## Контекст

Ряд ГУ перестаёт читать USB после пакета больше примерно 16 КиБ. Mazda 20622111: `VIDEO_DATA` 16518 и 19104 Б вешают
чтение, 16163 Б проходит. Mobis CCNC, наоборот, ждёт тело одним write, как пишет Baidu.

## Решение

- Глобально: 8-байтный внешний заголовок отдельным write, тело кусками не больше `Wire.CHUNK = 16384`
  (`Protocol.kt:249`, `writeSequence`; применяется в `StreamTransport.kt:150`). Так пишет ГУ Baidu, и на это рассчитан
  `f_accessory` (комментарий в `Protocol.kt:300`, спека §1.4 `docs/carlife-protocol.md`).
- Mazda 20622111: `VIDEO_DATA` больше 15000 Б режется на подряд идущие пакеты (`MAZDA_20622111_MAX_VIDEO_PACKET`,
  `AaBridge.kt:2645`), обложка в `MEDIA_INFO` не больше 12000 Б, `send()` отбрасывает любой пакет больше лимита с записью в лог
  (`CarLifeSession.kt:1150`).
- Mobis CCNC: заголовок и весь inner двумя write (`Wire.writeWhole`, `setWholeWrites`, `CarLifeSession.kt:603`).

## Альтернативы

- Общий кусок 16384 для Mazda: недостаточно, ГУ вешают уже 16518 Б, поэтому для неё взят лимит 15000 Б.
  Почему 15000, а не ближе к 16163: ? (спросить Егора)

## Последствия

- Нарезка Mazda рассчитана на то, что ГУ склеивает куски перед декодером (допущение, зафиксировано в комментарии кода).
- Любой новый пакет в сторону Mazda 20622111 обязан укладываться в лимит, иначе `send()` его молча отбросит.
- В `Protocol.kt` цифра 16384 объяснена только ссылкой на спецификацию; в PR #89 причина выбора числа не расписана.
