# tools

## logdiag.py — вероятная причина и что делать

На вход лог пользователя, на выход 1–3 вероятные причины с доказательством из лога, совет
пользователю и вопрос, который стоит задать. Работает поверх `logdigest.py`. Только stdlib Python 3,
запускается одинаково на Windows и Linux.

```
python -X utf8 tools/logdiag.py <архив.zip | папка | файл.log> [--json] [--all]
```

- `--all` — все сработавшие правила, а не только 3 лучших; `--json` — факты и причины структурой.
- Правила лежат данными в `logdiag_rules.json`: `markers` (regex по сырому логу, совпадения в
  пределах 2 с считаются одним событием) и `rules` с условиями `all`/`any`/`none` вида
  `[факт, оператор, значение]`. Операторы: `== != >= <= > < ~` (regex) и `<v`/`>=v` (версия).
  Факты: `m.<маркер>` — число событий; сводные из дайджеста — `n_sessions`, `frames_max`,
  `aa_video_max` (видео от AA, не кадры заглушки), `eio_sessions`, `eio_short` (оборваны по USB за ≤15 с),
  `no_gms`, `pause_eio` (EIO через 3–10 с после VIDEO_ENCODER_PAUSE), `version`, `sdk`, `hu`, `channel`,
  `requested`, `ep_<тип обрыва>`. Нет данных (`None`) не равно нулю.
- `score` — уверенность правила; `boost` добавляет к нему; `suppresses` гасит более общие правила;
  `fixed_in` — правило не срабатывает, если версия юзера не ниже, иначе к совету добавляется «обновитесь».
  `category: note` — заметка под причинами (старая версия, «всё работало»).
- Новая причина — новое правило в JSON и строка лога из реального кейса в `markers`. Проверка:
  `python -X utf8 -m unittest tools/test_logdiag.py`.

## logdigest.py — сводка по логам поездки

Сжимает архив логов Headswap в дайджест на 40–80 строк: окружение, таблица сессий,
обрывы, fps, ошибки, AUTOSRV, звук и микрофон, навигация, тач. Только stdlib Python 3.

```
python -X utf8 tools/logdigest.py <архив.zip | папка | файл.log> [--json]
```

Вход:
- zip из приложения («Поделиться отчётом»/«Сохранить архив»): `device.txt` + `logs/headswap-*.log`
  (в старых версиях `probe-*.log`), логи обрезаны до последних 4 МиБ;
- папка с полными логами, снятыми через adb (ищется рекурсивно, `logcat-*.txt` тоже подхватывается);
- отдельный `.log`.

`--json` выдаёт те же данные структурой, текст строится из неё же.

Что в разделах и откуда:
1. **Окружение** — `device.txt`; ГУ только из `HU_INFO` (строка `аксессуар:` — всегда Baidu CarLife, это не ГУ).
2. **Сессии** — от `== USB_ACCESSORY_ATTACHED` / `сессия: старт` до `== РЕЗЮМЕ СЕССИИ`; длительность и причина
   из резюме. `~` у времени начала — сессия началась до обрезки лога (время оценено). «лог кончился» — резюме нет.
   Колонка AA — главная AA-сессия (`AA итог`, наибольшее data), в скобках сколько их было (обычно вторая —
   короткая заглушка «мост остановлен»).
3. **Обрывы** — EOF, EIO/ENODEV, BYEBYE_REQUEST, USB_ACCESSORY_DETACHED, peer closed, POWER_DISCONNECTED
   из logcat («зажигание»); события в пределах 15 с склеены в эпизод. Флаг «без GMS» — EOF за ≤5 с после
   MEDIA_START (не MEDIA_PLAYBACK) при config=0 и 0 видеокадров.
4. **Видео** — `BRIDGE видео[...]` и `видео: отправлено ... (+N за 5с)`; интервалы вне 3–15 с отброшены.
5. **Ошибки** — `ERROR` и строки с `Exception`, цифры нормализованы.
6–9. AUTOSRV, звук/микрофон (`MIC_REQUEST` на NAVIGATION(10) — не микрофон), навигация (0x18043/0x18045,
   NAVI_NEXT_TURN_INFO), тач.

Дальше скаут грепает лог только в окнах вокруг времён из дайджеста.

Тест: `python -X utf8 -m unittest tools/test_logdigest.py`

## idr_splice_check.py — свой IDR на дампе AA

Проверяет на записанном потоке H.264 от Android Auto (например, дамп `pc-headunit`) то же, что делает
приложение с настройкой «Свой ключевой кадр раз в 2 с» (`aa/IdrSplice.kt`): подходит ли поток (CAVLC,
`max_num_ref_frames = 1`), какого размера получаются IDR (лимит 560 000 Б) и совпадает ли картинка бит-в-бит
после склейки и при входе с нашего IDR. Нужны numpy и ffmpeg.

```
python -X utf8 tools/idr_splice_check.py <дамп.h264> [--every 60] [--pcm-only]
```
